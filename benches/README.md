# queued_signal benchmarks

This crate holds the benchmark harness, the baseline ladder, and one binary per experiment.
It is a workspace member so the core crate's dev dependencies stay unchanged.

## Layout

- `src/lib.rs` re-exports the harness modules.
- `src/stats.rs` turns batched samples into p50, p99, p999, min, and max.
- `src/csv.rs` writes the fixed schema and creates the run directory.
- `src/manifest.rs` records the machine, compiler, commit, profile, and pin map.
- `src/isolation.rs` re-executes the binary once per row.
- `src/pin/` holds the platform affinity code, one file per platform.
- `src/settle.rs` flushes reclamation between rows.
- `src/bin/` holds one binary per experiment.
- `src/bin/resolve-parts.rs` attributes the frame resolve cost. It is a development tool, not an experiment, so it writes no CSV.

## Protocol

- One process per experiment.
- One process per row by default. A row that retires a generation leaves the receiver
  thread alive, so a shared process would read a previous row's reclaimer.
- Release or bench profile only. Debug numbers are not reportable.
- Warm up before timing and discard the warmup batches.
- Writer and reader on distinct cores when the machine has two. The map is recorded in
  `manifest.json` whether pinning succeeded or failed.
- The parent process never pins itself. A child inherits the affinity of the thread that
  spawns it, so pinning the parent would leave every row on one core and every contention
  row would report uncontended cost. A row pins the threads it owns after it reads the
  available cores.
- Thirty repetitions minimum per configuration.
- Report p50, p99, and p999. Never report a bare mean.

## Running

```
cargo run --release -p queued_signal_benches --bin e1-multiwriter
cargo run --release -p queued_signal_benches --bin e1-multiwriter -- --row 3
cargo run --release -p queued_signal_benches --bin e1-multiwriter -- --row-shared
cargo run --release -p queued_signal_benches --bin e1-multiwriter -- --smoke
cargo run --release -p queued_signal_benches --bin report
cargo run --release -p queued_signal_benches --bin resolve-parts
```

`--row-shared` runs every row in one process and is for development only. `--smoke` uses
small sampling and one repetition, and is what continuous integration runs.

## Results

The `report` binary also checks the E4 frame read. When both `b7-frame.csv` and `b6r-frame.csv`
exist, the b7 p50 at eight writers must stay under six times the b6r p50 at the same count, or
the command exits nonzero. The two rows run in the same pass, so machine drift cancels.

Every run writes to `results/<run_id>/<experiment>/`:

- `manifest.json` describes the machine and the build.
- One CSV per candidate and workload, named `<candidate>-<workload>.csv`.
- `summary.md` and `figures/*.svg` are generated by the `report` binary.

The CSV schema is frozen:

```
run_id,experiment,candidate,workload,param,param_value,metric,unit,p50,p99,p999,min,max,samples,rep
```

Tables and figures are always generated from these files. No number in a report is typed
by hand.

## Baselines

| Id | Design | Caveat |
|---|---|---|
| b0 | Direct field, no synchronisation | The floor |
| b1 | Signal a dioxus component keeps | Thread confined, so it cannot represent cross thread publication, and the framework does not expose how many scopes a write marked |
| b2 | Bevy resource reached through a system | ECS only, no renderer, and nothing registers for a wake |
| b3 | Reference counted read write lock | Lock holder blocks readers |
| b4 | Reference counted mutex | Lock holder blocks readers |
| b5 | One channel per subscriber | Per subscriber allocation, cost grows with N |
| b6 | Preallocated snapshot with a version counter | Fixed participant set, no wake path, readers retry across a write section |
| b6r | Preallocated snapshot rotating three slots | Single consumer, no wake path, a slow reader drops intermediate publications |
| b7 | queued_signal | The candidate |

## Figures

Figures are rendered with charton 0.9 from the CSV files and saved as SVG. The report
binary owns every chart, so the experiment binaries only produce data.

## Platform notes

Thread pinning uses the platform affinity call on Linux and on Windows. macOS exposes a
thread grouping hint rather than a pinning call, so a macOS row records the reason and
runs unpinned. A row never claims a core mapping it does not have.

## Scope

Multi process scale out is deferred. If it is needed, the shape is the same primitive in
N processes with a thin transport, measuring publish to consume latency and jitter.
